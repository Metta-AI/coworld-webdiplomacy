Design Proposal · 2026-10-12 · Status: Accepted on 2026-10-12, build starting

The League Desk: a local dashboard for running the webDiplomacy leagues

One read-only local page for the state of the press and gunboat leagues. By James Boggs with Claude.

Executive Summary

James runs two webDiplomacy leagues on the Softmax platform: the press league (Game of the Week, variant classic-press) and the gunboat league. Today the state of a league is spread over a dozen CLI commands and team-only API routes. Three settings changed on 2026-10-12 alone, and no single place shows what those changes did. This document proposes The League Desk: one dense, read-only page that runs on his machine and reads the Softmax API.

The design has three local parts, all synchronous Python: a collector that polls the API into a SQLite file, a metrics layer over that file, and one server-rendered page. A survey of the API on 2026-10-12 found a route for all but two of the platform metrics.1 Board metrics come from the public files each game already writes.2 Three metrics need small changes to the game, planned for Coworld 0.7.12. The most consequential decision is to keep a local cache, because the platform stores no rating history.

1 · Problem and goals

  • League state is spread over a dozen CLI commands and team-only API routes.
  • The goal is one local, read-only page that answers seven questions in order.

Three settings changed on 2026-10-12: the round interval (150 to 60 minutes), the daily budget ($15 to $100) and the game (Coworld 0.7.10, with 3-minute phases). There is no single place to see the effect.

The page answers, in order: does anything need action now, who is competing and how sure are the ratings, is the league keeping its schedule, what does it cost, how are players using LLMs and experience requests, who beats whom, and what happens on the board. Every panel states its finding in a sentence above the chart and names its data source. The dashboard never changes league settings.

Three things are out of scope. The page is not public, because it shows other users' private experience requests, email addresses and spend. It does not replace the Observatory site or the optimizer IDE, which is one player's view of one policy. It is not real-time, because a round takes about an hour and a refresh every minute or two is enough.

2 · The page

  • One dense page on a 12-column grid in the Softmax Ink & Print house style, with six sections.
  • Nine items go beyond the original request and are stated here as proposals.

The masthead controls are League (Press or Gunboat), Range (24 hours, 7 days, 30 days or All), Coworld version (All, 0.7.10 or 0.7.9) and Refresh. A new version can change game length, and therefore ratings, durations and cost, so every time chart marks the point where the version changed.

MMR is the rating the leaderboard ranks by. The league uses OpenSkill, a rating system that keeps two numbers per player: mu, its estimate of skill, and sigma, its uncertainty about that estimate. The rating interval in the standings table is mu plus or minus three sigma.

The design rules are fixed. The finding comes first and the chart second. Each chart has one y-axis. A reference line appears wherever a limit exists: the round interval, the budget, the seat cap and the par score of 0.143. A cell with fewer than five games is drawn empty and dashed, never coloured. Colour follows the entity. Terracotta marks a problem and is never reused for a data series.

How the page stays current

The page refreshes itself. Every 60 seconds it asks the local server for new panel contents and swaps them in place, so the scroll position and the chosen league, range and version stay as they are. The masthead shows the age of the data and has a control to pause the refresh. The refresh stops while the browser tab is hidden and runs at once when the tab is shown again. The Refresh button also tells the collector to poll the API now, without waiting for its next turn. A panel whose data failed to update shows its age in terracotta and keeps its last good contents.

How the sentence above each chart is written

Each panel has a sentence that states its finding. Code writes these sentences from the same numbers that draw the chart. No language model writes them. Each panel has a short list of rules in order of importance: a limit that was passed, the largest change in the selected range, an entity far from the others, and last a plain summary. The first rule that applies fills a fixed sentence pattern with the numbers. Because the sentence comes from the cached data when the panel is drawn, it is as fresh as the chart and changes on the same 60-second refresh. A sentence can never state a number that the chart does not show. The "Needs attention" list is written the same way, from thresholds in one configuration file.

The proposed additions beyond the original list are the "Needs attention" list, version markers and the version filter, league spend against experience-request spend, membership and exposure, filler share, time from submission to first game, phase timing, seat health, and a data-source tag on every panel.

4 · What the API survey found

  • Two platform gaps: per-round rating history, and the LLM model a policy was uploaded with.
  • Experience requests cost about 130 times what the press league cost in the week read.

These facts were read on 2026-10-12. All but two of the platform metrics have a route.1

A team-only, read-only SQL route exists, POST /sql/query.5 It has a 20-second timeout and returns at most 1,000 rows, cut off silently. It is the only way to get LLM spend per seat in bulk and the stored request spec of experience requests.

Only rounds 7 to 9 are visible in the press league, because earlier rounds were hidden when rounds were reset on 2026-10-12.1 History charts start there. Rate limits are generous for one user: 1,500 requests a minute and 12,500 an hour. The admin cost and usage routes are unpaginated scans, so the collector polls them slowly.3 Experience-request rows carry the requester's email address.6

Finding For the week read on 2026-10-12, the press league's tournament spend was about $10.83, and experience-request spend on the same Coworld was about $1,422.3 The daily league budget of $100 counts tournament spend only. This is why the page sets league spend against experience-request spend.
Unverified The per-episode cost_usd field is compute only, and LLM spend is attributed separately. The round cost route reported $0.00 of LLM spend for a round whose league shows LLM spend for the same week.3 Treat per-round LLM cost as unverified.

5 · Architecture

  • Three local parts: a collector, a metrics layer and a page. All are synchronous Python.
  • A page load reads only the local cache and never calls the API.

Collector. It polls the API with James's own login and the elevated-privileges header, and writes rows to a local SQLite file. It asks only for rounds, episodes and requests newer than what it holds. It takes the rating snapshot after each completed round, and it downloads results.json and the replay of each finished league game, which the optimizer's fetch_league.py already does.16

Metrics. SQL views and small Python functions over the SQLite file. Board metrics reuse the optimizer lab's loader and tools (webdip_episodes.py, matchups.py, board_counts.py and batches.py) instead of new parsers.16

Page. One server-rendered page from a small FastAPI and Jinja app, the same stack the optimizer IDE in this repository already uses.17

The code lives in ops/league-desk/ in this repository as its own uv project, like optimizer/ide. It is not part of the optimizer template, because players cannot call the team-only routes. The SQLite file and the downloaded artifacts stay in an ignored directory. The app prints no tokens and binds to localhost only.

6 · Decisions and rejected alternatives

  • Four decisions, each with the alternatives that lost.
  • Five existing dashboard tools were surveyed on 2026-10-12 before choosing a small custom page.
Decision 1

The dashboard keeps a local SQLite cache. Rating history does not exist on the platform, so something must store snapshots anyway.1 The cost routes are slow scans.3 Artifacts must be downloaded once and parsed.

Rejected: query the API on every page load. It is slow, it loses rating history, and it repeats the cost scans.

Decision 2

The page is a FastAPI and Jinja app that reuses the pattern of the optimizer IDE. That stack is already in this repository, with the same dependencies and the same test style.17 It gives full control of a dense single page in the house style and stays synchronous.

Rejected: Streamlit (the most popular Python dashboard tool, Apache-2.0, released 2026-10-02).18 It is the fastest route to a first version, but a dense 12-column page with custom table cells, shared-scale interval bars and the house style fights its layout model. It is the right choice if speed matters more than the single-page design.

Rejected: Grafana (AGPL-3.0, very active).18 It is strong for time series and alerts, and weak for the standings table, the matchup grid and board charts. It also means running a server and a data-source plugin for a one-person tool.

Rejected: Evidence (MIT, reports from SQL and Markdown) and Observable Framework (ISC, last push 2026-05-15).18 Both are static-site builders that fit the data. Each adds a Node toolchain to a Python repository, and Observable Framework's activity has slowed.

Rejected: marimo (Apache-2.0, active).18 It is a notebook, which is good for exploration and not for a fixed operations page.

Decision 3

Observable Plot draws every chart (ISC). James left the choice open, and Plot is the faster of the two to build with for this page: one short call per chart, against a long options object in ECharts for the interval, cell and small-multiple charts. The file is pinned and served from the local app, so the page works without a network. It draws SVG that the page's CSS can style, and it handles dot-and-interval, cell and line marks directly. Its release pace is slow: the latest release is dated 2025-02-14 and the last push 2026-09-01.18 Apache ECharts is the fallback for that reason.

Rejected: hand-drawn SVG. The mock-up's charts are hand-drawn only because it is a static mock-up.

Decision 4

Board metrics are read from each game's public files. The results.json file and the replay already hold scores by power, adjudicated orders and phase transitions.298

Rejected: new platform features. They are not needed, because the public files already hold this data.

Decision 5 (added after review)

Ready timing and missed orders go to the public game log, in one line that the game writes when the game ends. Private press counts wait for a team-only artifact. James decided on 2026-10-12 that Ready timing can be public after the game. The line is never written during play, because upstream hides Ready status from the other players while an anonymous game runs. The platform serves results.json and the game log to anyone with access to the episode, and the game also sends the results to every player when the game ends.2120 A dedicated team-only telemetry artifact is requested from the platform team (Asana task 1219425581082710). Press counts are not recorded until it exists.

Rejected: the trajectory file. It is team-only and needs no platform change, but it exists for training data and its reader does not expect other lines. Rejected: results.json. The game sends it to every player in the last message of the game, and it is the scoring record, not a log.

Decision 6 (added after review)

Rules and fixed sentence patterns write the sentence above each chart. They cost nothing, they give the same sentence for the same data, and they cannot state a number that the chart does not show.

Rejected: a language model writes the sentences. It reads better, but it costs money on every refresh or goes stale between runs, it can state a number wrongly, and it changes its wording when the data did not change. A written summary once a day is a possible later addition, shown apart from the panels and marked as written by a model.

8 · Build order

  • Step 1 needs no game change and delivers most of the page.
  • Each later step adds one data source.
  1. API-only page. Sections 1 to 5 of the page and the head-to-head grid. No game change is needed.
  2. Artifact ingest. Score by power, contested provinces, end reasons and phase timing.
  3. Coworld 0.7.12 with instrumentation items 1 to 5. This adds the timing profile, time to Ready and seat health.
  4. Platform timing split from Datadog job traces, joined to the game's timing record.13

9 · Open questions

James answered the first seven on 2026-10-12. Question 8 was added after review and is also decided. No question is open.

Open 1 Once Ready timing and missed-order data are recorded, do they go into results.json, which every player in the game receives,20 or into a team-only artifact? Publishing them after the game tells rivals how each bot behaved.
Decided 2026-10-12: the public game log, written when the game ends. See decision 5.
Open 2 The same question applies to private press counts. The recommendation is per-seat totals only, or a team-only artifact.
Decided 2026-10-12: a team-only artifact. Deferred until the platform has one (Asana task 1219425581082710).
Open 3 Rating history: is "history starts when the dashboard first runs" acceptable, or do we also backfill by replaying OpenSkill, which may not match the platform's numbers exactly?
Decided 2026-10-12: history starts when the dashboard first runs. No backfill.
Open 4 The SQL route is an internal team tool and could change. Is it acceptable for per-seat spend and request overrides to depend on it, or do we ask the platform team for proper routes?
Decided 2026-10-12: acceptable for now.
Open 5 Experience-request spend is about 130 times league spend this week and has no budget. Is that intended? The dashboard shows it either way.
Decided 2026-10-12: intended. The panel stays.
Open 6 Will anyone besides James use this? It shows email addresses and private requests.
Decided 2026-10-12: only James. No sharing or sign-in features.
Open 7 Charting library: Observable Plot or Apache ECharts?
Decided 2026-10-12: Observable Plot. See decision 3.
Open 8 (new) Where does the team-only record go? The platform has one team-only file that a game can write today: the trajectory file, which exists to hold training data.21 The game can write its operations record there with no platform change. The cost is that the file then holds lines that the platform's training-data reader does not expect, which matters only if someone exports training data from webDiplomacy games. The clean alternative is a small platform change: a new team-only artifact for game telemetry. The recommendation is to use the trajectory file now, with every line marked as an operations record, and to ask the platform team for the dedicated artifact.
Decided 2026-10-12: neither file. Ready timing and missed orders go to the game log. The dedicated artifact is requested, and press counts wait for it.
